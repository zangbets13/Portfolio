01 — OVERVIEW

The problem

Manual small-cap catalyst research is slow and unscalable: pulling gainers lists, cross-referencing news, and judging whether a price move was a clean trend or a spike-and-fade by eye doesn't scale past a handful of tickers a day — and doing it every trading day, without fail, at 6:30am before market open, isn't realistically sustainable by hand.

The goal was a system that could (1) discover genuinely fresh, same-day catalysts rather than yesterday's already-known winners, (2) build a growing historical dataset of which catalyst types and sectors actually produce reliable price trends, and (3) track its own hit rate over time, so its usefulness could be measured rather than assumed.

03 — KEY DECISIONS & PROBLEMS SOLVED

What actually went wrong (and how it got fixed)

Continuation bias in candidate selection

Early design mistake: the morning scan pulled candidates from yesterday's gainer list — a subtle but critical strategy flaw, since it biases toward stocks that already made their move rather than discovering fresh, same-day catalysts. Rebuilt the scan to pull from Polygon's News API directly (last 16 hours), decoupling historical pattern-building from live candidate discovery entirely.

Filtering out non-tradeable instruments

A significant share of "top gainers" lists were warrants, leveraged ETFs, and preferred shares — instruments with no real market cap and no independent catalyst. Added a common-stock-only filter using Polygon's instrument-type metadata, applied before any expensive classification work runs, improving data quality and cutting API cost at the same time.

Cost optimization on LLM calls

An early version made one search-enabled Claude call per ticker (100/day) — expensive and inefficient. Refactored into two tiers: cheap, vision-only calls for chart-shape classification, and separate batched search-enabled calls (10 tickers per call) for catalyst research, cutting cost by roughly 60% while improving catalyst identification accuracy through a more focused per-batch search budget.

A silent data-corruption bug

Discovered that the outcome-logging job was using a "most recent close" endpoint rather than a date-specific one — on market holidays, it silently reused stale prior-day data and mislabeled it as the current day's outcome, producing a systematic (and misleading) 100% win rate. Fixed by switching to exact-date queries with explicit holiday detection, plus building verification and manual-correction tooling to spot-check data against outside sources.

Shared state across dev and production

Migrated from a local JSON file — which caused local runs and the cloud deployment to silently diverge — to a shared, cloud-hosted PostgreSQL database, so the developer's machine and the production scheduler now read and write the exact same source of truth.

Observability

Job failures (like API credit exhaustion) were originally silent — no output, nothing until manually checking cloud logs. Added automatic failure-notification emails to every scheduled job, so any break in the pipeline surfaces immediately instead of being discovered by absence.

04 — RESULTS & VALIDATION

Does it actually work?

The system currently maintains 400+ classified historical records across multiple trading weeks, with ongoing pattern analysis surfacing statistically-flagged, sample-size-aware insights — for example, contract-win catalysts showing large average moves but low follow-through consistency, versus biotech earnings beats showing smaller but more reliable trend continuation.

Rather than assume the system works, a dedicated track-record module cross-references every prediction against its actual next-day outcome, explicitly checking whether the model's own confidence scores correlate with real performance — a calibration check, not just a win/loss count.
